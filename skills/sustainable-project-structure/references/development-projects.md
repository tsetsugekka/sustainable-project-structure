# 开发项目结构

## 目标

让页面、服务或工具成为明确的维护单元，使源码、专属 API、测试、部署资料和文档能随同一个所有者目录演进。

## 所有权与可选编号

- 优先保留页面、服务、工具等已有职责目录；编号可选，不复制其他项目的数字含义。
- 采用编号时，在根治理文件中写明其业务意义；非页面公共区可以使用高位编号，例如 `80+`。
- 部署、共享运行代码、项目文档、通用工具、Skill、归档和临时区沿用已有归属，只创建实际需要的目录。
- 子路由留在所属页面内，不把每个 URL 都提升为根目录。

可选的页面所有者结构；既有 web/pipeline/docs 或其他责任清晰的布局无需迁移：

```text
<number>_<PageName>/
  README.md
  public/                 # 页面入口或前端源码
  api/                    # 页面专属 API（按需）
  private/                # 非公开运行模块（按需）
  assets/                 # 页面专属资源（按需）
  tools/                  # 页面专属 worker/collector/cron
  tests/                  # 页面专属测试
  docs/
    READMECHS.md
    SPEC.md
    CHANGELOG.md
    history/              # 已完成设计和实施计划（按需）
    qa/                   # 页面 QA 证据（按需）
```

## 按职责维护文档

持续维护的模块应覆盖以下职责，文件名只是例子。优先复用既有名称，小模块可以合并，简单改动不必补齐三份文件：

- `docs/READMECHS.md`：如何运行、维护、测试、部署、排障；说明入口和关键依赖。
- `docs/SPEC.md`：当前有效行为、页面结构、数据流、权限、接口和限制，是当前语义事实来源。
- `docs/CHANGELOG.md`：按时间记录已经发生的功能、结构、迁移和运维变化，不写尚未实现的愿望。

页面根 `README.md` 是简短入口，指向相关文档并解释目录。修改代码时只同步受影响内容。文档留在所属模块，长短时效、去重归并、归档和自动目录遵循 [文档生命周期](documentation-lifecycle.md)。根入口只收长期入口，任务和批次记录从本地查阅。

## 共享边界

- 只服务一个页面的代码、测试和工具归页面所有。
- 账号、权限、全局导航等平台能力归系统页面或平台目录。
- 两个以上页面运行时共同依赖的代码归共享运行区，并明确消费者。
- 跨页面重复执行且稳定的维护工具归项目工具区；一次性脚本先留在临时区。
- 本地源码目录与线上 URL 分离记录。目录迁移后更新部署白名单，但不擅自改线上路由。

## 开发项目验收

- 每个持续维护单元有清楚的入口，并按复杂度覆盖操作、现行规格和重要变更职责。
- 页面专属源码、API、测试和工具不再散落在系统目录或根目录。
- 部署清单源路径全部存在，测试与构建通过。
- 根级缓存、`node_modules`、截图和试验输出已清理或忽略。
- 检查与真实目录规则一致，目录可重建且过期能被发现；不以模板文件是否齐全代替知识维护。
